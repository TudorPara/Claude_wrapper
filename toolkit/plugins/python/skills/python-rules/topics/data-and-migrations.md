# Nexttech data model and migrations

A source such as `#5` is a pull request of `nexttech-assistant-svc`. The project's data doc specifies its own tables, columns, constraints and indexes: implement exactly that, because two people who disagree about a column produce migrations that collide. Anything else (an extra column, another name) is a deviation and is explained in the PR.

## 1. ORM models

- ORM models live in `schemas/`, one file per table. `Base` lives in `schemas/base.py` (#5; #11).
- Every ORM model is exported from `schemas/__init__.py`, because Alembic registers models by importing that package.
- ORM classes are singular; tables keep the names in the data doc, singular or plural as written there (#5).
- `doc="..."` on every column (#5).
- Primary keys are uuid version 7, generated by the application with `uuid.uuid7()`, so the id is known before the insert (#5). The default is applied at flush: flush before another row needs the id.
- Times are `timestamptz`, always: `DateTime(timezone=True)`.
- Every table extends `Audit` (`created_at`, `updated_at`).
- Where `Audit` has no `eager_defaults`, `updated_at` is expired after an ORM UPDATE and reading it outside the session raises `DetachedInstanceError`. A repository method that updates through the ORM and returns the entity refreshes the row after the flush.
- Text is `text`, never `varchar(n)`. A length limit is validation and belongs in the API.
- Reference a person by `user_id`, never by email (#8).
- No second definition of a table or an enum that another PR already owns.

## 2. Enums of stored values

- The enums of stored values live in `models/`, one file per domain, never one `enums.py`.
- Every value is UPPERCASE with underscores (`ALL_STAFF`, `INDEX_DOCUMENT`, `QUEUED`): "These should be uppercase" (#4, #5, #6). Where a doc lists the same values in lowercase, the enum wins.
- Enum columns are native PostgreSQL enum types (the mentors' decision, #5), declared like this:

```python
role: Mapped[Role] = mapped_column(
    Enum(
        Role,
        name="user_role",
        values_callable=lambda members: [member.value for member in members],
    ),
    primary_key=True,
    doc="Role granted to this user: EMPLOYEE, HR, or ADMIN.",
)
```

- Adding or removing a value later is a hand-written migration; autogenerate does not see it. The migration manages the type explicitly: `create_type=False` on the column, and the type dropped in `downgrade`.
- A value that is not stored, such as a folder name, is not an enum value: convert with `.lower()` and `.upper()`.

## 3. Constraints

- Every constraint is named explicitly: `uq_<table>_<columns>`, `ck_<table>_<meaning>`, `ix_<table>_<columns>`, `fk_<table>_<column>_<target>`.
- An invariant the docs or a docstring state is a check constraint, not application code (#5).
- Counters get a server default of 0 and a non-negative check (#5).
- A one-column rule (`unique`, a check) goes on the column itself (#8).
- `ondelete` tells one story for a table whose rows are never deleted (#5).
- One table plus derivation beats two tables that must stay in sync.

## 4. Migrations

- `alembic/env.py` reads `DATABASE__URL` from the environment, runs on an async engine and targets `Base.metadata`. Run Alembic as the Makefile does: `PYTHONPATH=. uv run alembic <command>`.
- Tables come from `make migrate` only. Never `create_all`: it bypasses the migrations.
- Model and migration match exactly: types, timezone, nullability, constraint and index names. `alembic check` prints "No new upgrade operations detected".
- Exactly one head. Branches that each add a revision produce two heads at merge: after merging `main`, run `alembic heads`, and if there are two, regenerate your revision on top of the new head.
- Read every autogenerated revision before applying it. Never leave a body as `pass`. `downgrade` undoes `upgrade`, and must not fail on a row that is already gone (#5).
- Never edit a migration that is on `main`; add a new one (#6).
- `Revises:` in the header matches `down_revision` (#8).
- A rename uses `op.rename_table` or explicit operations; autogenerate drops and recreates.
- A feature branch does not add a migration for a table another task owns.
- One local database shared by all branches: before switching, downgrade the migrations the target branch lacks, or keep one database per branch.
- Resolve a generated file by regenerating it, never by editing it: the lockfile, a migration, a cache.
- Leave the local database as you found it. Say what you created or dropped, and ask before dropping a table that holds rows.

## 5. Conventions carried over from the nexttech-assistant-svc data doc

The project's own data doc wins where it differs.

- A column meaning "when this happened" is `created_at`: there is no `granted_at`, `indexed_at`, `started_at` or `opened_at`.
- An email column is `citext`; the extension is enabled in the first migration.
- Lists are tables; a nested document is `jsonb`. Store only what the client cannot re-render.
- A `metadata` column holds operational breadcrumbs only (the request id, which model answered, how long it took). Never anything a feature reads, the client renders or anyone queries.
- People are deactivated, never deleted.
